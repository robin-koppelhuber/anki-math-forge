{# The complete state machine, derived from the code rather than from memory. Laid out the way the sketch asks for it: the states you move through run down the middle, and everything optional (the assistive passes, what an object carries, the annotations) sits in a column to the right. Nothing in that column moves anything, which is the whole reason it is a column rather than a row of boxes in the spine. What is easy to get wrong here, all of it checked against the source: * `carded` and `draft` are one moment, not two steps. `/extract-cards` writes the card file and marks the unit carded in the same call; there is no state where one has happened and the other has not. It is a split: from here on there are two objects, and the rest of the machine is about the second one. * `/transcribe` and `/classify` do nothing for a source whose units came from marks. A highlighted paragraph already carries its text, and the two classifier rules are about a page of formulas. Both skills say so and stop. `/gist` is the one unit pass that runs on either, because the gist-writer reads the mark's own sentence where there is one. * `/classify` reads the transcription in preference to the PDF text layer, so it wants `/transcribe` first. Not a hard dependency: it still works on an untranscribed book, from the worse of the two readings. That is why the arrow between them is dashed like the rest and not a state edge. * A card is not one card per unit, in either direction, which is why `queued` to `carded` is drawn as a fan and not a line. `Card.units` reads `unit:` as a list, so several units merge into one card, which is what a multi-line display cut into pieces by a segmenter wants. `Unit.uids` is a list and `Ledger.mark_carded` appends to it, so one unit splits into several cards. Both are properties of the format, so both are drawn; how often either happens is a fact about somebody's deck and belongs nowhere near a diagram of the machine. * `Ledger.set_state` permits any unit state to any other and the triage view binds q/s/u unconditionally, so `u` is not "undo a skip": it returns any unit to new, a carded one included. * Only an approved card is demoted by an edit (`Card.effective_status`). A draft edited stays a draft, so a card can be revised any number of times before anyone approves it. * An annotation is not a state and does not attach to a particular box. It can sit on any unit or any card, from either side, and it blocks sync from any of them, which is why its one outgoing arrow points at the sync gate. Arrows to individual boxes would claim something untrue. * Traffic to Anki is one-way with a single exception, and the exception is an arrow: `feedback` takes a comment or a flag out of Anki and writes it as an annotation, erasing it there in the same pass. It arrives at the annotations box because that is what it becomes, not at a state. There is one `new` box and not two. A unit is `new` in the ledger whatever door it came in by, so drawing the state twice would say there are two of them in the diagram people read to find out what the states are. The branch is real, but it is a branch in which passes you can run, so it is drawn where it happens: on the passes. No caption. The picture was carrying eight lines of prose under it, which is a second explanation of the same thing in the one place a reader is already being shown it. What is worth saying in words is said where the diagram is opened from, and the rest is up here where the person editing the SVG is the one who needs it. Two of the boxes in that column are not passes. `on a unit` and `on a card` say what an object carries, and drawn like the rest they read as a fourth and fifth thing to run. They have no border, a rule down the left instead, and a plain line back to the state rather than an arrow: an arrowhead is for something that acts. Geometry is checked by tests/test_fsm.py: no overlapping boxes, no edge through a box, no overlapping labels, no edge through a label. Hand-authored SVG does not stay correct on its own. #}
